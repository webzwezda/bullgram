# Магазин аккаунтов: приёмка паков → отлёжка → публичная витрина → выдача

Статус: концепция на обсуждение владельца. Кода нет.
Исследование: три Explore-разведки (импорт/safe-mode, магазин/оплаты, прокси/тиры) 2026-10-26 + разбор папки `~/Desktop/teleak`.

## Идея одним абзацем

Мы (платформенный админ) закидываем на `/userbot/connect` пачку аккаунтов (папка/zip с паками вида
`<phone>.session + <phone>.json + tdata/ + txt с паролем 2FA`). Сервис разбирает паки, каждому аккаунту
автоматически поднимает выделенный прокси, кладёт сессию в safe-mode (`pending_activation`) и «отлёживает»
— фоновая проверка здоровья (getMe → frozen-проба → SpamBot) по одному аккаунту за раз. Больные уезжают
в уже построенный Отстойник, в продажу не попадают. Витрина аккаунтов — публичная, без регистрации,
оплата TON. Покупатель-аноним получает одноразовые ссылки на архив аккаунта (.session + .json + tdata +
пароль 2FA + readme). Покупатель с регистрацией дополнительно получает аккаунт к себе в кабинет
(смена owner_id) с доступом в Telegram Web; без Pro из safe-mode он может поднять только один купленный
аккаунт — остальные лежат до апгрейда. После продажи «в файлы» наша копия аккаунта и прокси зачищаются.

## Подтверждённый формат пака (teleak)

```
+13637778642.zip
├── +13637778642/
│   └── tdata/ (минимальный: maps, s, key_datas)
├── +13637778642.json     ← TelegramExpert fingerprint (app_id, device, …)
├── +13637778642.session  ← sqlite, 32 КБ
└── FAQ + Пароль 2фа ….txt ← пароль 2FA (кодировка CP1251)
```

Правило группировки: файлы с общим базовым именем (номер) = один аккаунт; `tdata/` прикрепляется к
своему номеру; zip может содержать много аккаунтов (подпапки или россыпью). Формат подтверждён на трёх
паках с рабочего стола.

## Чего нет (строим)

1. **Распаковка архивов**: в backend нет zip-библиотеки; multer на импорте = 2 файла × 2 МБ.
2. **Batch-импорт**: все пути импорта — один аккаунт за синхронный запрос; нужен джоб-конвейер.
3. **Автовыдел прокси при импорте**: сейчас `proxy_id` обязателен от клиента.
4. **tdata + пароль 2FA**: нигде не хранятся (импорт их явно отклоняет); в `userbot_restore_sources` нет колонок.
5. **Файловая выдача**: в backend нет ни одного download-роута; only ownership transfer.
6. **Анонимное создание покупки**: `POST /shop/public/purchase` требует JWT; `buyer_owner_id` NOT NULL.
7. **item_type='account'**: в enum магазина только proxy/userbot/bundle/channel_audience_asset/text_offer.
8. **Публичная витрина**: userbot-v2 глобально за логином (App.jsx:79); site-v2 `/shop` — сейчас тупо редирект.
9. **Отлёжка**: ни один джоб не проверяет pending_activation сток платформы.
10. **Гейт активации покупателем** (Pro = 1 активация): активация (`/check?activate=true`) квоту не проверяет вовсе.

## Архитектура

### Этап 1 — Приёмка (только платформенный админ)

- UI: на `/connect` (userbot-v2) новая вкладка «Партия аккаунтов» рядом с QR/Импортом: drag&drop зипов
  и/или кнопка выбора папки (`webkitdirectory`), предпросмотр найденных аккаунтов (номер, что нашлось:
  session/json/tdata/2fa, валидность), кнопка «Импортировать N аккаунтов», прогресс по каждому.
- Backend: `POST /api/userbot/intake/batch` (multer: файлы + `paths[]` из webkitRelativePath; лимит
  пачки 100 аккаунтов / 200 МБ). Асинхронно: создаёт `account_import_batches` (новая таблица: owner,
  статус, счётчики, отчёт jsonb) и обрабатывает по одному:
  1. распаковка/группировка по базовому имени;
  2. валидация (.session sqlite-header, .json api_id/api_hash) — без подключения к Telegram;
  3. дедуп по tg_user_id не делаем на этом шаге (нужен getMe) — дедуп по auth_key fingerprint от парса;
  4. `provisionManagedProxyBatch` (по одному, `inventory_group='self_use'` — это хостинг стока, не прокси-лот на продажу);
  5. вставка `tg_accounts` с `runtime_status='pending_activation'` (все существующие джобы сразу оставляют его в покое);
  6. `saveRecoverySource` ОБЯЗАТЕЛЬНО + новые колонки: `tdata_blob_encrypted`, `tdata_filename`,
     `two_fa_secret_encrypted` (пароль из txt, CP1251→UTF-8), `intake_batch_id`.
  7. на ошибке аккаунта — компенсация (release proxy), запись в отчёт, пачка продолжается.
- SQL (одна миграция, через postgres-pro ревью): колонки `userbot_restore_sources`, таблица
  `account_import_batches`, `shop_purchases.buyer_owner_id` → nullable.

### Этап 2 — Отлёжка

- Джоб `intake-resting.job.js` (флаг `USERBOT_INTAKE_RESTING_ENABLED`, интервал ~12ч): берёт
  `pending_activation` аккаунтов платформенного админа, поднимает по одному (пауза 20–30 сек,
  таймауты уже есть в env), `getMe` + `inspectAccountHealth` (включая frozen-пробу):
  - здоров → пишет `last_checked_at` + health-details, **статус остаётся pending_activation** (safe-mode сохраняется — это важно для Pro-гейта, см. этап 4);
  - болен → статус по диагнозу (frozen/restricted/expired/dead_proxy/error) → сам падает в Отстойник,
    существующие гейты продажи его не пропустят.
- Кнопка «Проверить» из Гигиены работает как сейчас (ручная активация — только осознанно).
- Прайсинг: ручной, пачкой — «выставить N проверенных аккаунтов по цене X» в разделе магазина.

### Этап 3 — Витрина (публичная)

- Локация: **site-v2, маршрут `/shop`** (сейчас там редирект — заменяем на настоящую витрину).
  userbot-v2 глобально за логином — публичный роут там означал бы дыру в глобальном гейте;
  site-v2 уже публичный и `/pay/:purchaseId` уже умеет анонимный shop-чекаут. Витрина показывает
  карточки лотов `item_type='account'` (номер-маска, цена TON, свежесть проверки, «Telegram Web в подарок
  при регистрации») + существующие прокси-лоты. Без логина.
- `shop_items.item_type='account'`, ассет `asset_type='userbot'` (переиспользуем), новый флаг
  `delivery_mode`: `files` (аноним) / `hybrid` (файлы + трансфер при регистрации) / `transfer` (как сейчас).
- Backend: `POST /api/shop/public/purchase-anon` (`optionalAuthenticateUser`): если есть JWT — пишем
  `buyer_owner_id`, иначе NULL. Всё остальное (бронь 30 мин, гейты карантина, memo, verify-public,
  claimPaid) — уже существует и работает без логина.
- Гейты продажи для account-лотов: ужесточаем смысл — публикация требует свежей чистой проверки
  (≤6ч, health ok, SpamBot clear, frozen-проба чиста), независимо от pending_activation;
  блоклист плохих статусов остаётся. Правка вчерашнего гейта: pending_activation со свежей проверкой
  — продаваемый сток, а не карантин.

### Этап 4 — Покупка и выдача

**Сценарий А — аноним (только файлы):** оплатил по `/pay/:purchaseId` (TonConnect или перевод по memo)
→ verify-public → paid → на странице оплаты появляется блок «Скачать аккаунт»: одноразовые ссылки
`GET /api/shop/public/purchase/:id/download/:token` (HMAC-токен, TTL 72ч, лимит 5 скачиваний, IP rate-limit).
Бэкенд на лету собирает zip: `.session` + `.json` + `tdata.zip` + `пароль-2fa.txt` + README «как запустить».
Одновременно: лот → sold, аккаунт помечается `payload.sold_delivery='files'`, джоб через
`SHOP_FILES_PURGE_DELAY_HOURS` (72ч, окно на ре-выдачу/поддержку) зачищает: restore source, tg_account,
выделенный прокси (release 3proxy-слота). Мы не продолжаем жить в проданном аккаунте.

**Сценарий Б — с регистрацией:** покупка создана под JWT → paid → `transferShopAssets` как сейчас
(аккаунт + его прокси переходят покупателю, `provision_source='purchased'`) → аккаунт появляется у него
в `/userbot` **в safe-mode** + кнопки «Telegram Web» и «Скачать архив». Подъём из safe-mode — кнопка
«Активировать» (существующий `/check?activate=true`): **новый гейт** — купленный аккаунт у покупателя
без Pro: активен может быть один; второй клик → 403 «Купленные аккаунты: без Pro активируется один.
Остальные ждут в safe-mode. Перейди на Pro». Реализация: при активации если у покупателя есть
завершённые shop-покупки аккаунтов, считаем его уже-активированные (runtime_status ≠ pending_activation):
≥1 и tier ≠ pro → отказ. Для этого трансфер-гард для account-лотов ослабляется: принимает
`pending_activation` **со свежей чистой проверкой** (наша отлёжка), остальные плохие статусы по-прежнему
запрещены.
- Анонимный покупатель может «до-регистрироваться»: на странице покупки кнопка «Создать аккаунт и
  забрать в кабинет» → регистрация/логин → claim покупки по её id → трансфер задним числом.

### Этап 5 — Учёт и поддержка

- Казна: обе схемы пишут `shop_purchases` с `seller_owner_id` = платформенный админ → `/treasury`
  видит выручку автоматически; для анонимных храним `payload.sender_wallet` (уже принимается в
  verify-public) как ключ поддержки.
- Журнал продаж аккаунтов: существующий журнал покупок в userbot-v2 + фильтр по item_type='account'.

## Где я правлю исходную картинку (обсуждение)

1. **Витрина — на site-v2 `/shop`, не публичный роут в userbot-v2.** userbot-v2 защищён глобальным
   AuthGate (App.jsx:79); проделывать публичную дыру в приложении-кабинете хуже, чем отдать витрину
   публичному сайту, у которого уже есть анонимный чекаут. Приёмка на `/connect` — да, как ты и сказал.
2. **Активация покупателем — обязательно из safe-mode.** Если бы продаваемый аккаунт уже был «online»,
   Pro-гейт «одна активация без Pro» не имел бы смысла. Поэтому отлёжка проверяет здоровье, но НЕ выводит
   аккаунт из safe-mode; вывод — акт покупателя (или наш ручной, когда надо).
3. **Прокси на приёмке — расход стока, а не товара.** Каждый аккаунт в стоке держит managed-прокси;
   глобальный лимит 512 (из них 256 на админа). Сток в ~100 аккаунтов — это треть ресурса. Либо поднимаем
   лимиты (наша же /64-подсеть), либо после чистой отлёжки отпускаем прокси до момента продажи и
   переподнимаем при продаже. Рекомендую сначала просто поднять лимиты, не усложнять.
4. **RAR — позже.** В v1 zip + папка. `node-unrar-js` существует (wasm), но это лишняя поверхность на
   первый релиз; селлеров просим zip. Добавим по факту спроса.
5. **Пароль 2FA — часть пака, не опция.** Приёмка парсит txt (CP1251), хранит зашифрованным и отдаёт
   покупателю. Это же закрывает историю «пароль на рабочем столе» — поле появится у каждого
   импортированного аккаунта. Авто-ротацию 2FA на приёмке (чтобы селлер потерял доступ) закладываем,
   но делаем отдельной волной — этоSensitive-операция, нужен отдельный прогон.
6. **Нашles копии после анонимной продажи зачищаются.** Иначе мы держим живую сессию проданного
   аккаунта на своём прокси — риск для нас и для покупателя.

## Решения владельца (2026-10-26, все закрыты)

- Парсинг — **один общий модуль** на все сценарии (приёмка/выдача): примитивы в `userbotService`, группировка паков в новом `account-pack.service.js`; «поменял в одном месте — изменилось везде».
- Чек здоровья в карточке лота — **да**; проверка НЕ выводит аккаунт из safe-mode (проба поднимает сессию, статус не трогает, обновляется только отчёт). Покупатель видит последний чек; свежесть на публикации ≤6ч + отлёжка каждые 12ч не дают ему протухнуть. Живую проверку по кнопке покупателю не даём (поверхность абьюза) — только последний отчёт.
- Номер в карточке — **маска** (`+7…642`); полный номер — только после покупки.
- Пачки — **до 100 аккаунтов** за раз.
- Минимальная отлёжка — **делаем**: `SHOP_ACCOUNT_MIN_REST_HOURS` (default 48) на этапе публикации (волна 2).
- Для отчёта о здоровье добавляется колонка `tg_accounts.health_summary jsonb` (пишут resting-джоб и ручная проверка).

## Риски

- **Правовой/ToS**: передача аккаунтов против правил Telegram — платформа уже живёт с этим риском
  (магазин юзерботов работает); отлёжка + Отстойник + честный health-отчёт снижают «продали мёртвое»,
  но не снимают риск банов после продажи. Держать окно поддержки/возврата.
- **Селлер знает 2FA и имеет .session/tdata**: до авто-ротации пароля купленный аккаунт формально
  остаётся у селлера. Отлёжка это не лечит. Митигция волной ротации; до неё — честно в карточке лота не обещать «пожизненно».
- **Одна пачка = много живых коннектов**: только последовательный подъём с паузами, иначе флажим
  наш же датацентр-паттерн перед Telegram.
- **Одноразовые ссылки = единственный ключ**: потерял `/pay/:id` — потерял доступ; поддержка по
  memo/tx-hash + sender_wallet.
- **Новые зависимости** (`adm-zip` или `unzipper` для zip) — строго в том же коммите (Dependency rule).

## Верификация (по Browser Doctrine — на проде)

1. Импорт паков из teleak (тестовая пачка 2-3 аккаунта) → сток в safe-mode, прокси выделены, отлёжка зелёная.
2. Сломанный пак (нет .json, битый sqlite) → отчёт с ошибкой, пачка не падает, прокси не утекает.
3. Витрина без логина в чистом браузере: лот виден, покупка создаётся, TON-оплата по memo, файлы скачиваются, повторное скачивание ограничено.
4. Покупка под тестовым аккаунтом без Pro: аккаунт приехал в safe-mode, первая активация ок, вторая купленная — 403; после Pro-апгрейда — активируется.
5. Казна: продажа видна в `/treasury`, прокси и аккаунт зачищены после files-продажи.
