# Правила продажи аккаунтов (tdata + отлёжка) и объединение складов

Статус: план на подтверждение владельца. Изучено по коду 2026-11-03.
Предыстория: владелец предложил объединить «Продажу аккаунтов» и «Юзерботы на витрине»
(2026-10-31/11-01) и сформулировал правило: «продаже подлежат только аккаунты с tdata
архивом и отлёжкой».

## Факт-чек: как продаются правила СЕЙЧАС (по коду)

| Правило владельца | Сейчас в коде | Вердикт |
|---|---|---|
| Только с tdata-архивом | tdata на приёмке **опционален** (пак без tdata проходит, `account-intake.service.js:178`); в архиве покупателя tdata.zip «если был в комплекте» (`shop-delivery.service.js`, buildShopFileArchive) | **НЕ выполняется** — аккаунты без tdata продаются |
| Отлёжка | Свежая чистая проверка ≤6ч обязательна (гейт публикации + scan sellable). Но **минимального срока нет**: импортировал → проверил → продавай в тот же час. `SHOP_ACCOUNT_MIN_REST_HOURS` из волны-2 так и не реализован | **Частично** — есть свежесть, нет выдержки |

Плюс из прошлого обсуждения — объединение складов: скан-карточка должна видеть всех
юзерботов админа (с паков и рабочих), но продавать — только по правилу владельца.

## Правило (фиксируем в коде)

Аккаунт подлежит продаже, когда выполняется ВСЁ:
1. **tdata-блоб сохранён** (`userbot_restore_sources.tdata_blob_encrypted is not null`)
   — комплект покупателя полный;
2. **Отлёжка пройдена**: свежий (≤6ч) health-чек `online` (как сейчас);
3. **Выдержка**: с импорта прошло ≥ `SHOP_ACCOUNT_MIN_REST_HOURS` часов (default 48,
   env-конфигурируемо; в карточке показываем «Отлёжка 5ч из 48 — рано»).

## Работы

### Волна A — правила в гейты (бэкенд + карточка)
1. Скан: для каждого айтема тянем `tdata_blob_encrypted is not null` и `created_at`
   (candidates-запрос уже берёт restore sources — добавим поля). `sellable` требует
   tdata + выдержку; иначе вердикты-причины в «Проблемных»: «Нет tdata-архива» /
   «Отлёжка 9ч из 48».
2. Батч-гейт `createAccountLotsBatch`: те же проверки + понятная ошибка. Гейт
   files→intake уже есть, объединяем в один блок правил.
3. Карточка: группа «Проблемные» уже рендерит причины — новые причины подхватятся;
   кнопка скана без изменений.
4. `.env.example` + README: `SHOP_ACCOUNT_MIN_REST_HOURS`.
5. Тесты: без tdata → failed; выдержка < N → failed; ровно на границе → ok.

### Волна B — объединение складов (админ)
1. Скан-кандидаты: **все** юзерботы админа (и без restore source тоже — рабочие
   QR-импорты). Для них режим «Только кабинет» недоступен: без tdata они не
   подлежат продаже по правилу → попадают в «Проблемные» с причиной «Нет tdata-
   архива: продажа невозможна» (честно видно, что товар не из приёмки).
2. Батч-эндпоинт: всегда создаёт `account`-лоты delivery_mode='hybrid'; параметр
   deliveryMode из карточки уже убран.
3. Секция «Юзерботы на витрине» с `/connect` **у админа убирается** — её функции
   (список своих лотов, снять с витрины) переезжают в объединённую карточку
   (блок «Уже на витрине» + кнопка «Снять с витрины» на строке).

### Волна C — витрина и legacy-лоты (после решения владельца)
- Открытый вопрос 1: снимать ли `userbot`-лоты (рабочие юзерботы, transfer-only)
  с публичной витрины `/shop` совсем? Предложение: да — витрина показывает только
  `account`-лоты; userbot-лоты остаются возможны технически (unlisted/бандлы),
  но на витрину не попадают.
- Открытый вопрос 2: секция «Юзерботы на витрине» у Pro-продавцов (маркетплейс
  своих юзерботов) — остаётся, или Pro-продажа тоже переходит на account-лоты?
  Предложение: остаётся как есть (это чужой товар, наше правило — про наш сток).

## Не делаем
- Авто-генерацию tdata из session (синтетика = другой товар).
- Ротацию 2FA в этом правиле (волна 4: при ротации обновлять пароль в блобах).
- Прогонку скана по расписанию (уже есть отлёжка; скан — по кнопке).

## Верификация
1. Аккаунт без tdata в скане → «Нет tdata-архива», выставить нельзя (батч-гейт).
2. Свежий импорт (5ч) → «Отлёжка 5ч из 48», нельзя; через 48ч после скана → можно.
3. Витрина: у всех account-лотов полный комплект в архиве (проверка скачивания).
