# Продажа аккаунтов: кнопка «Найти аккаунты» — скан всех хранилищ с живой проверкой

Статус: план на подтверждение владельца. Кода нет.
Контекст: сейчас карточка «Продажа аккаунтов» на `/connect` показывает кандидатов автоматически
(live-юзерботы админа с restore source из приёмки). Владельцу это не нравится: непонятно, откуда
список, карантиные аккаунты молча исчезают (пришлось дописывать строку «лежат в отстойнике»), и
свежесть проверки не привязана к моменту продажи.

## Требование владельца

Кнопка «Найти аккаунты для продажи», которая:
1. смотрит **все места**: основное хранилище аккаунтов (боевые, safe-mode, ручные импорты) и отстойник;
2. **проверяет сессии на месте** — реальный living-check (connect через прокси → getMe → frozen-проба →
   SpamBot), как кнопка «Проверить Telegram», а не чтение старых статусов;
3. выводит список с вердиктами, из которого админ выбирает и выставляет.

## UX (карточка «Продажа аккаунтов»)

- Вместо авто-списка — блок скана: кнопка «Найти аккаунты для продажи» + дата/результат последнего скана.
- Кнопка → `POST` скана → карточка в режиме прогресса: «Проверяю X из N» (поллинг статуса, как в приёмке
  пачки). Дисклеймер: «Проверка живая, по ~30–60 сек на аккаунт — пачка из 10 займёт ~8 минут».
- По завершении — группы:
  - **Живые — можно выставлять** (вердикт online / safe-mode с чистой проверкой): чекбоксы, выбор, цена,
    существующая кнопка «Выставить»;
  - **Проблемные** (restricted / frozen / expired / dead_proxy / error) — вердикт и причина, без чекбокса,
    с пометкой «лежит в отстойнике» у карантинных;
  - **Блобы без аккаунта** (restore source есть, tg_account удалён) — информационная строка «можно
    восстановить через Restore на /userbot», кандидатами не становятся (v1).
- Результаты скана персистентны: перезагрузка страницы показывает последний скан. Сканируешь заново —
  список обновляется. Протухание: если скан старше 6ч, бейдж «Проверка устарела — прогони скан» (гейт
  публикации ≤6ч на бэкенде остаётся без изменений и сам не пропустит).
- Строку «Ещё N в отстойнике» убираем — скан теперь сам показывает карантинных с вердиктами.

## Архитектура

1. **Единый код проверки.** Логика «connect → getMe → inspectAccountHealth → применить статус с
   карантинными эффектами» сейчас живёт в `jobs/intake-resting.job.js` (`checkIntakeAccount` + блок
   применения результата). Выносим в `services/intake-stock.service.js`: `checkStockAccount(...)` и
   `applyStockVerdict(...)` (запись runtime_status/health_summary/identity, restricted → событие +
   unpublish + чистка прокси, frozen → событие + unpublish, duplicate-guard). Джоба отлёжки и скан
   зовут одно и то же — «поменял в одном месте». Джоба продолжает работать по расписанию (12ч),
   скан — тот же чек по требованию.

2. **Таблица `account_sale_scans`** (миграция `backend/sql/account-sale-scan.sql`, стиль wave-1/2:
   `set lock_timeout`, RLS без политик, rollback-блок, `notify pgrst`): id, owner_id, status
   ('processing'|'completed'|'failed', CHECK), total/processed, items jsonb (по аккаунту: label, verdict,
   reason, checked_at), created_at/updated_at. Индекс (owner_id, created_at desc). Stale-свип
   «processing > 1ч → failed» в обоих GET (как у приёмки).

3. **Эндпоинты** (admin-only, в `shop.routes.js` рядом с account-lots):
   - `POST /api/shop/admin/account-lots/scan` — создаёт scan-строку, fire-and-forget запускает обход:
     кандидаты = юзерботы админа, у которых есть restore source (любой статус, включая карантин;
     сортировка: сначала не проверявшиеся давно). По каждому — `checkStockAccount` + `applyStockVerdict`,
     пауза `USERBOT_INTAKE_RESTING_SLEEP_MS` (25с, анти-флуд), прогресс пишется после каждого айтема.
     Одновременный скан одного владельца — запрещён (активный processing → 409). Аккаунты без прокси —
     вердикт «нет прокси» без Telegram-подключения.
   - `GET /api/shop/admin/account-lots/scan` — последний скан владельца (полный, с items) + stale-свип.
   - Существующий `POST /admin/account-lots/batch` не меняется: его гейты (свежесть ≤6ч, health online,
     files → intake) остаются единственной точкой истины при выставлении — скан лишь гарантирует свежесть.

4. **Фронт (`AccountLotsSection` + хук)**: кнопка → POST → поллинг GET → рендер групп; выбор только из
   «живых»; «Выставить» вызывает существующий batch-эндпоинт; после выставления — строка «Лоты видны на
   /shop». Авто-список из `state.accounts` удаляется (как и строка «Ещё N в отстойнике»). Пропсы
   `accounts`/`quarantinedIntakeCount` уходят.

5. **Документация**: `.env.example`/README — новых env нет (переиспользуем sleep/timeout отлёжки),
   только раздел README про скан; AGENTS.md флаги не меняются.

## Инварианты

- Последовательная проверка с паузами — никаких параллельных коннектов (анти-флуд, как в отлёжке).
- Скан пишет статусы честно: проблемный аккаунт после скана уезжает в карантин с теми же эффектами,
  что у отлёжки (unpublish, чистка прокси на restricted); выздоровевший карантинный — возвращается.
- Гейт публикации не ослабляется: скан не «продажа», бэкенд-проверка при выставлении остаётся.
- Чужие данные не трогаем: скан только по `owner_id` админа; restore source читается, не пишется.
- Деструктива нет: скан ничего не удаляет (кроме карантинных эффектов restricted, как у отлёжки).

## Не делаем (v1)

- Восстановление блобов без аккаунта в кандидаты (только информационная строка).
- Параллельные/ускоренные сканы, выборочная проверка подмножества (кнопка на аккаунт).
- Авто-скан при открытии страницы (только по кнопке + показ последнего).
- Сканирование чужих лотов/покупателей.

## Тесты

- scan-runner: кандидаты из всех статусов (боевой/safe/карантин/без прокси), прогресс после каждого
  айтема, 409 на второй скан, stale-свип; вердикты применяются через applyStockVerdict (restricted
  чистит прокси, frozen сохраняет, duplicate-guard).
- эндпоинты: admin-gate, публичный доступ запрещён.
- фронто-логика — существующие гейты (build + check:design), без новых юнит-тестов (кухня та же).

## Верификация (по Browser Doctrine)

1. Скан на живом стоке: 2 боевых + 1 замороженный → прогресс → группы 2/1, статусы в базе обновлены.
2. Сломанный кейс: аккаунт с мёртвым прокси → вердикт dead_proxy, в «Проблемные», лот выставить нельзя.
3. Повторный скан во время идущего → 409, карточка не ломается.
4. Выставление из результатов скана → лоты на /shop (гейт ≤6ч проходит, т.к. скан свежий).

## Ревью и прод-прогон (2026-11-01)

- **Код-ревью: SHIP AFTER FIXES → закрыто.** P1: частичный уникальный индекс «один processing-скан
  на владельца» (миграция 20261029120000), 23505 → 409 «Скан уже идёт». P3: кандидаты передаются
  из POST в раннер (total и items не расходятся), ошибка проверки не помечается карантином,
  кап поллинга нейтральным тоном. P2 (HTTP-тесты роутов) — BACKLOG §26.
- **Живой прогон QA-агентом нашёл три вещи, две настоящие:**
  1. **Флак getMe**: `+19…332` в первом скане дал error «не отдал профиль», будучи живым. Фикс:
     один повтор getMe перед вердиктом (`checkStockAccount`).
  2. **«Выздороветь» было невозможно**: healthy-вердикт консервировал статус снапшота — error от
     флака оставался навсегда, и скан отдавал противоречие «verdict error + reason живой». Фикс:
     живой результат ставит правдивый `online` (safe-mode сохраняется), тест-регрессия на run-2.
  3. «Авто-старт скана при перезагрузке» — не подтвердился: единственный POST-путь это кнопка;
     агенту встречные клики. Индекс + дизейбл кнопки делают спам невозможным.
- Результаты скана персистентны (таблица), последний скан переживает перезагрузку.
