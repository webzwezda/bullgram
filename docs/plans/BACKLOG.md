## §25. Тёмная тема: у китовых hover нет dark-пар

Решение: при появлении тёмной темы в продукте добавить dark-пары hover в канонический кит — `outline` hover `hover:border-border-strong hover:bg-surface-subtle-strong` не имеет `dark:hover:*` (светлый slate-300/100 на тёмном фоне), `default` hover `bg-primary/80` тоже композиится только под светлые подложки. Заодно решить edge case precedence expanded+hover на select-триггерах. Владелец: платформа. Триггер: решение о тёмной теме (сейчас её в продукте нет, замечание дизайн-критика волны hover 2026-10-22).

## §27. Автовозврат лота на витрину после здоровой проверки

Решение: джоба `listed-userbot-health.job.js` снимает лот при карантинном вердикте (`error`/`dead_proxy`/`expired`) без события в БД, а автовозврата нет — лот остаётся `draft/private` даже когда следующая проверка даёт `online` (комментарий в джобе «восстанавливается после живой проверки» кодом не обеспечен). Варианты: (а) при вердикте `online` авто-репаблик лотов, снятых той же джобой по карантинному вердикту (хранить причину снятия, например в `updated_at`+лог или отдельной таблице/метке), (б) минимум — событие в `telegram_error_events` при карантинном снятии, чтобы инцидент был виден без pm2-логов, плюс подсказка в UI продавца «лот снят автопроверкой, аккаунт здоров — вернуть?». Инцидент-пример: 2026-11-04 14:57 +10 пяти секундный SOCKS-таймаут прокси-слота на 193.23.197.169 при плановой автопроверке снял account-лот +13…642 с /shop; прокси и аккаунт восстановились в тот же день, лот вернули вручную 2026-11-05. Владелец: платформа. Триггер: второй случай «лот пропал с витрины без видимой причины» или решение владельца по (а)/(б).

## §32. Авто-выдача managed-прокси каждому новому пользователю (владелец, 2026-11-07) — РЕАЛИЗОВАНО 2026-11-07, ждёт включения флага
Построено: JIT-выдача при создании юзербот-аккаунта (не при регистрации —
GoTrue минует backend; «1 аккаунт = 1 прокси» по правилам платформы).
`allocateManagedProxyForAccount` — атомарный claim свободного слота
(owner_id IS NULL, username mp_*), хуки в qr/sessions non-fatal, исчерпание
→ TG-алерт с дедупом 1ч. Числа решения: пул поднят 2026-11-08 —
218 слотов, 200 свободных (план docs/plans/2026-11-08-proxy-pool-200.md),
флаг `USERBOT_AUTO_ALLOCATE_PROXY_ENABLED=false` всё ещё выключен.
Триггер: слово владельца (тариф-правило: слот любому или только Pro) →
включить флаг в backend/.env.
Открытым остаётся тарифная логика (бесплатный слот vs лимиты тарифа) —
владелец; квоты на пользователя и очистка слота при удалении аккаунта —
в следующий заход, не блокируют включение.

**Бесшовный флоу (слово владельца 2026-11-07 «зарегался → подключил ТГ →
работает»)**: построено и задеплоено за тем же флагом (d2aa6b5, c084607).
Без proxy_id роуты qr-start/qr-status/import-session-file сами занимают
свободный слот ДО подключения к Telegram (force_ipv6-зеркало loadOwnedProxy),
возвращают его в пул при любом провале и на ретрае QR; фронт /connect и
инлайн-панель — поле прокси опционально с подсказкой; pool_empty → текст
пользователю + алерт владельцу. Флаг off → прежнее поведение байт-в-байт.
Кандидат-долг: TTL-свип «заклеймлен-без-аккаунта» слотов (владелец бросил
QR-экран, не сделав ни одного qr-status — слот остаётся у него; ретрай и

## §35. Telegram Web: коллизия сессий при двух вкладках (найдено 2026-11-15)
Два таба `/userbot/telegram-web/<id>` (разные аккаунты) делят один origin:
localStorage/IndexedDB у форка один — второй таб рендерит сессию ПЕРВОГО
под URL второго (воспроизведено на проде: вкладка Сандры показывала чаты
Elizabeth). Решение: ключовать хранилище форка по id аккаунта из URL
(префикс БД/ключей) либо открывать Telegram Web в вынесенном origin
(`telegram-web.<domain>`). Решение: агент. Триггер: первый пользователь,
который откроет двух юзерботов рядом (владелец уже столкнулся).
## §36. DM-резолвер: whitelist сервисных ботов (BotFather/SpamBot) (2026-11-15)
`resolveDirectMessageTarget` требует существующий диалог/общий чат —
легитимно для холодных DM, но делает неосуществимым завязку диалога с
сервисными ботами платформы; при этом `botfather.mixin` умеет
(`getInputEntity('botfather')`). Диагностика инцидента BotFather упёрлась
в это. Решение: в резолвер — whitelist известных id (BotFather 93372553,
SpamBot 178220800) с прямым resolveUsername. Решение: по слову владельца.
