# Runbook: сигнатуры логов и реакции

Аудитория: агент/разработчик на дежурстве. Дайджест (cron srv `0 */4 * * *`,
`/opt/alerts/log-digest.sh`) шлёт в Telegram топ error/warn за 4ч и ссылается
сюда. Алерты несут только факты и расшифровки — реакции живут здесь (решение
владельца 2026-11-11: инструкции дежурному агенту — отдельными скиллами).
Формат логов и команды чтения — [`logging.md`](logging.md).

Общий принцип: сигнатура → понять сцену (кто/что сломалось) → реакция по
таблице ниже. Не глушить источник (не «чинить» лог молчанием) — чинить причину.

## Сигнатуры

### 1. `401: Unauthorized` / `[bot-rights-monitor] Error checking rights for bot <uuid>`

Мёртвый или отозванный токен BotFather-бота (пример из суточных: боты
`fe6b923c…`, `ccd2bbee…`). Права бота не проверяются, функционал владельца
(автопост, права в каналах) деградирует молча для арендатора.

**Реакция**: найти бота по uuid (`select id, name, owner_id from autopost_bots
where id like '<prefix>%'` через Supabase MCP) → проверить токен live-запросом
(`curl api.telegram.org/bot<token>/getMe`) → токен мёртвый: сообщить владельцу,
арендатору нужно перевыпустить токен в BotFather; до замены — бот не трогается.

### 2. `409` на `getUpdates` / `Conflict: terminated by other getUpdates request`

Двойной поллинг одного токена: два процесса читают одну очередь (второй инстанс
backend, забытый тестовый процесс, или чужой consumer). Поллинг обоих падает
циклически.

**Реакция**: `pm2 list` — нет ли дублей; `ps aux | grep node`; на сервере
второго инстанса быть не должно. Если источник внешний (арендатор вставил токен
в свой скрипт) — сообщить владельцу. См. BACKLOG §27 (наблюдение 2026-11-06).

### 3. `Proxy connection timed out` / GramJS таймауты на юзерботах одного прокси

Деградация прокси-хоста (суточная норма: 20-30 таймаутов на хост
`193.23.197.169`). Health-check джоба карантинит/снимает с витрины лоты при
таймауте — известный инцидент: /shop показал один лот вместо двух
(2026-11-05), см. BACKLOG §27 (нет авто-возврата и DB-события карантина).

**Реакция**: посчитать таймауты по хосту
`jq -r 'select(.level=="error" and .err.message|test("timed out")) | .proxy_host? // "?"'`
(поле смотрится по месту) → единичные — норма, пропустить; всплеск по одному
хосту → проверить хост, сообщить владельцу о замене; лот, снятый с витрины без
причины — проверить `shop_lots`/карантин и вернуть вручную (авто-возврата пока
нет — BACKLOG §27).

### 4. n8n-скан: `warn` 404 на `/api/v1/*`, `/api/config`, `/healthz`

Интернет-сканеры ищут открытый n8n на нашем домене (~750 warn/сутки). В
дайджесте отфильтрованы (тест `^/api/(v1|config)|^/healthz`) — если видишь их в
дайджесте, сломан фильтр. Отдельно не реагировать; option nginx 444 —
волна 2, п. 2.7.

### 5. `connect ETIMEDOUT 2001:b28:f23d:f001::a:80` (api.telegram.org по IPv6)

Исходящий IPv6 VDS до api.telegram.org не отвечает (глюк провайдера/маршрута).
Telegraf/GramJS могут ретраить на IPv4 сами — тогда это редкий warn; если
переходит в систематические падения исходящих вызовов Telegram — принудить
IPv4-резолв на исходящих вызовах (отдельным решением).

**Реакция**: единичные — пропустить; пачками за 4ч — проверить
`curl -6 https://api.telegram.org` с сервера и сообщить владельцу.

### 6. `job failed` / `job finished (slow)` (≥30с)

Провал или замедление cron-джобы (обёртка `wrapJobTick`, поля `job` + `runId` +
`durationMs`).

**Реакция**: взять `job` из записи, найти её код (`backend/jobs/`,
`backend/services/`), посмотреть контекст той же `runId` — соседние записи
тик-а. Разовая — пропустить; повторяющаяся — баг-репорт + фикс.

### 7. `source: "web"` — клиентские ошибки SPA

Фронтовая ошибка из log-capture (6 аппов, `POST /api/log`). Поля `web_app`,
`message`, `stack`.

**Реакция**: воспроизводить на проде реальным Chrome (Browser Doctrine, не
headless и не dev-сервер); по стеку найти файл в соответствующем аппе.

## Команды (копипаста)

```bash
ssh srv
# живой поток ошибок
tail -f /srv/bullgram/backend/logs/app.out.jsonl | jq 'select(.level=="error")'
# топ причин за 24ч (как в дайджесте, но окно 24ч)
SINCE=$(date -u -d '24 hours ago' '+%Y-%m-%dT%H:%M:%S')
jq -r --arg since "$SINCE" 'select(.time > $since) | select(.level=="error" or .level=="warn") | select((.req.url // "") | test("^/api/(v1|config)|^/healthz") | not) | [ .level, (.req.url // .job // .module // "-"), ((.err.message // .msg) // "-") ] | @tsv' \
  /srv/bullgram/backend/logs/app.out.jsonl | cut -c1-80 | sort | uniq -c | sort -rn | head -15
# диск/память/дампы/пул
df -h /; free -m; ls -lht /backups/postgres | head -3
```

Связанное: [`logging.md`](logging.md) · алерты: `/opt/alerts/*` на srv ·
открытые хвосты — `docs/plans/BACKLOG.md` §27.
